## A. 데이터 계층

### A1. DB 시퀀스 → 애플리케이션 사이드 TSID

- **배경/제약**: 초기 스키마(V25120701)는 테이블당 전용 시퀀스 24개 + `@SequenceGenerator(allocationSize=1)` — INSERT마다 `nextval` 왕복 [확인: 46b37e2 diff]. 프론트는 무한 스크롤/페이지네이션 중심이라 시간 정렬 가능한 ID가 유리한 도메인.
- **검토된 선택지**: UUID를 실제로 검토했고, 시간 정렬성 우위로 TSID 채택 [증언 — Q9]. 비교 문서가 Confluence에 있었으나 현재 접근 불가(수개월 미접속) [증언] — 면접 전 복구 시도 가치 있음.
- **최종 선택**: `tsid-creator` 5.2.6, NODE_BITS=8(256노드), 커스텀 `IdentifierGenerator` [확인: common/util/tsid/]. **2단계 도입** — 신규 도메인(boast, 246e3c2, 12-22)에서 먼저 검증 후 이틀 뒤 전 엔티티 33개 확산 + 시퀀스 30개 CASCADE 드롭(46b37e2 + V25122403, 12-24) [확인].
- **트레이드오프**: (얻음) INSERT 왕복 제거·시간 정렬성·분산 생성 가능 / (포기) DB 레벨 ID 발급 보장, ID에서 생성 시각 유추 가능(정보 노출) [추론], 64-bit라 JS 정밀도 문제 유발 → A2로 연쇄.
- **결과**: 이후 ID 관련 스키마 변경 없음. Tsid.java 수정 이력 0 — 최초 설계값 유지 [확인].

### A2. 응답 DTO의 ID를 Long → String으로 전환

- **배경/제약**: TSID 64-bit 값이 JS `Number.MAX_SAFE_INTEGER`(2^53-1) 초과 → 프론트에서 ID 뒷자리 유실 [확인: 커밋 메시지 "JS에서 53bit까지만 읽어들여, id값이 누락되는 이슈 해결"].
- **검토된 선택지**: ① 응답만 String 직렬화 ② JSON 직렬화기 전역 설정(Long→String) ③ 프론트에서 BigInt 파싱. PR #51 본문에 "진짜 이렇게 해야 되나? 실무에서도 이렇게 해?"라는 자문이 남아 있음 [확인] — 업계 표준(Twitter Snowflake의 id_str 등)과 일치하는 선택이었다는 답을 면접에서 붙일 수 있음.
- **최종 선택**: 전 모듈 DTO 일괄 String 전환 — 33개 파일, TSID 확산 커밋 3시간 뒤 같은 날 [확인: 0e6a8ca, PR #51].
- **트레이드오프**: (얻음) 프론트 호환 / (포기) 타입 안전성 일부, DTO마다 `String.valueOf` 반복. 전역 직렬화기 대신 명시 변환을 택한 이유는 흔적 없음 [추론: 명시성 선호 또는 미검토] → 질문.
- **결과**: 이후 신규 DTO(draft 등)도 String 규칙 준수 — 규칙으로 정착 [확인].

### A3. DB FK 제거 (studio 경계 14개) + 크로스 도메인 Long id-ref 규칙

- **배경/동기 [증언 — Q1]**: **예방적 결정.** 실무자 피드백 — "FK를 걸어두면 실사용자 이슈 대응 시 FK 제약 때문에 대응이 막히거나 늦어질 수 있다" — 를 받고, **"DB 레벨은 완화하고 코드 레벨에서 제약을 강화한다"**는 원칙으로 전환. 실제 FK 위반 사고를 겪은 건 아님.
- 부차 정황 [확인]: 소프트 딜리트 확장(V26012501)과 한 커밋 — 소프트 딜리트 확산이 실행 타이밍의 계기였을 가능성.
- **검토된 선택지(흔적)**: 두 관행이 실제로 **한 달간 공존** — monte의 신규 테이블(boast, 12-24~25)은 FK 주석 처리 생성, sehee의 동시기 테이블은 FK 계속 생성 [확인: V25122401/V25122503 vs 팀원 마이그레이션].
- **최종 선택**: V26012502(d887210, 2026-01-25, PR #88)에서 studio 계열 10개 + subway 계열 4개 FK 드롭. 동일 커밋에서 studio 서브엔티티 소프트 딜리트 확장(V26012501) — **FK 제거와 소프트 딜리트 확장이 한 커밋** = 소프트 딜리트가 직접 동기라는 정황 [추론 — 강함]. 이후 CLAUDE.md에 규칙화(a6709fa, 03-08): "DB 레벨 외래키 제약 없음", "타 도메인은 PK만 참조", "@OneToMany 금지" [확인]. **실행이 먼저, 문서화가 나중.**
- **트레이드오프**: (얻음) 소프트 딜리트/삭제 순서 자유, 도메인 경계 명시(Long id-ref가 경계를 코드에 드러냄) / (포기) DB 무결성 보장 — 정합성이 애플리케이션 서비스 레벨 책임으로 이동, 고아 행 가능성. **부작용 [확인]**: PostgreSQL은 FK 참조측 자동 인덱스가 없어 애초에 인덱스가 없었고, 드롭 후에도 `rooms.studio_id` 등 조인 키가 여전히 미인덱스 — FK 드롭과 무관하게 존재하던 갭이 드러남.
- **결과**: musician/terms 등 팀원 도메인 FK는 현존 — "전면 제거"가 아니라 **studio 경계 한정** 결정 [확인]. 범위 서술에 주의.

### A4. 소프트 딜리트 3종 공존 + partial unique index (부분 공동 결정)

- **배경/제약**: 탈퇴/삭제 후에도 데이터 보존 필요(신고 증거, 재가입, 통계) + 유니크 제약(닉네임/전화번호)과 소프트 딜리트의 충돌.
- **최종 선택**: 대상 성격별 3종 — ① 일반 엔티티: `deleted_at IS NULL` + `@SQLDelete`/`@SQLRestriction` ② 코드성 마스터(Term, FaqCategory 등): `is_active` 플래그 ③ 사용자 계정(Owner, Musician): `deleted_at` + `status='INACTIVE'` 플립 + `hard_delete_at`(유예 후 하드삭제). 유니크 충돌은 **partial unique index**(`WHERE deleted_at IS NULL`)로 해결 — 탈퇴자 닉네임/전화번호 재사용 가능 [확인: V25122101, V26010901].
- **저자 주의 [확인]**: `SoftDeletableEntity` 계층은 최초 커밋(1c0075f, monte)부터. musicians partial unique(V25122101)는 monte 커밋이나 user 도메인 담당은 Sehee라 발의 주체 단정 불가. owners(V26010901)와 deleted_at NOT NULL 완화 3건은 **Sehee 저자 — 맥락 전용**.
- **트레이드오프**: (얻음) 데이터 보존 + 재가입 UX / (포기) 모든 쿼리에 암묵 predicate(@SQLRestriction), 3종 방식의 인지 비용, `deleted_at` NOT NULL→NULL 완화 3회의 시행착오 [확인 — Sehee 영역].

### A5. Flyway 도입 + `ddl-auto: validate`

- **배경**: 초기엔 마이그레이션 도구 없이 개발(2025-10~12-06). 팀 2인 + dev/prod 2환경에서 스키마 드리프트 위험.
- **최종 선택**: PR #27(12-07)에서 Flyway 도입, 기존 스키마를 V25120701로 베이스라인화. 전 프로파일 `ddl-auto: validate` + `baseline-on-migrate: true`(태스크 기동마다 실행) [확인].
- **트레이드오프**: (얻음) 스키마 이력 버전화, 컨테이너 기동 시 자동 적용 / (포기) 엔티티 선언 인덱스·유니크가 자동 반영 안 됨 → 엔티티-SQL 드리프트 다수 발생(raw/data-model.md 불일치 목록) [확인]. validate는 nullability를 검사하지 않아 드리프트가 무증상.

## B. 지리공간 검색

### B1. 뷰포트 검색 = envelope(st_intersects) + QueryDSL 템플릿

- **배경/제약**: 지도 화면의 바운딩 박스 내 스튜디오 조회가 핵심 UX. 서울 중심 서비스라 데이터 규모는 작게 시작.
- **검토된 선택지(흔적)**: 반경 검색(ST_DWithin)은 studio 검색에 시도 흔적 전무 [확인: pickaxe] — 처음부터 envelope. 네이티브 SQL 대신 QueryDSL `Expressions.booleanTemplate`으로 PostGIS 함수 주입 — 13개 동적 필터와의 조합성이 이유로 추정 [추론].
- **최종 선택**: `st_intersects(location, st_makeenvelope(...4326))` — 첫 커밋(d80dddc, 11-25)부터 현재와 동일 형태 [확인]. location은 `geography(Point,4326)`.
- **트레이드오프**: (얻음) 동적 필터와 한 쿼리 합성, 타입 세이프 쿼리 빌딩 / (포기) geography-geometry 암묵 캐스트 발생, **GiST 인덱스 미생성**(마이그레이션에 없음 — 시퀀셜 스캔) [확인]. 인덱스 부재가 의도인지 누락인지 → 질문.
- **결과**: 2단계 ID→엔티티 쿼리 + 정렬 화이트리스트도 첫날 함께 도입 [확인: 3a4f986]. 검색 코어는 2026-01-25 이후 무변경.

### B2. 도보 시간 제거 → Java Haversine 직선거리

"10초당 5회 제한" 기억의 귀속은 재확인 중 — 유력 가설: 대량 스튜디오 입력용 벌크 지오코딩(`findNearbyStationsInBulk`, 호출자 0 데드코드)이 Juso rate limit로 폐기된 건 (Q6 갱신).

- **트레이드오프**: (얻음) 검색당 외부 API 비용 0, 지연 감소 / (포기) 도보 시간이라는 더 유용한 정보 → 직선거리로 다운그레이드.

### B2-b. 지오코딩 = 공공데이터 도로명주소 API(Juso) 채택

- **[확인]** 도입: 12-01 주소 검색(a817e48, **Sehee** — 회원가입 나의 작업실) → 12-03 `JusoApiClient` 정식화 + proj4j EPSG:5179→WGS84 변환(401ea46, monte). 카카오/네이버 지오코딩을 쓴 흔적은 전 이력에 없음 [확인: pickaxe].
- **채택 이유 [증언 — Q6]**: ① 무료 ② **결정적으로 DB 저장 정책** — 카카오 등 민간 지도 API는 결과 좌표를 DB에 저장하는 것이 약관 위반인데, 도로명주소 검색 API는 **전화로 직접 문의해 "DB 저장 무방" 안내를 받고** 채택. 컴플라이언스를 유선 확인까지 한 실사(due diligence) 사례 — 면접 소재로 강함.
- **"10초당 5회" rate limit의 귀속 [증언 — Q6 확정]**: 가설대로 **벌크 지오코딩 작업이 Juso rate limit에 걸려 폐기**된 건 — `findNearbyStationsInBulk`가 호출자 0 데드코드로 남은 이유.
- **트레이드오프**: 2단 API 호출(검색→좌표) + 5179 좌표계 변환 부담(proj4j 도입), rate limit(벌크 작업 불가).
