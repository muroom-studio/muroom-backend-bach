# 파일 스토리지 3번의 시도 — 버킷 하나에서 정책 enum까지

*[Muroom 회고 시리즈](/writing/muroom-aws-on-pocket-money)의 리팩토링 편: 두 번 다시 쓴 S3 레이어, 그리고 마침내 성장을 멈춘 버전.*

---

스튜디오 하나가 이미지를 최대 40장씩 달고 다녔습니다 — 도면, 룸, 옵션 사진. 온보딩 때는 우리가, 나중엔 커뮤니티 글로 사용자가 올렸습니다. 이걸 처리하는 S3 레이어는 넉 달 동안 두 번 다시 쓰였는데, 각 버전은 이전 버전의 *실제* 문제를 풀었고, 마지막 버전은 리팩토링으로서 드문 일을 해냈습니다: 기능을 늘리면서 코드베이스를 *줄였습니다*.

## V0: 버킷 하나와 for 루프

베타는 동작하는 가장 단순한 것으로 나갔습니다. 단일 버킷, presigned PUT URL(브라우저가 S3에 직접 업로드 — `t4g`급 인스턴스에서 이미지 바이트가 JVM을 통과하게 두고 싶지 않습니다), 그리고 파일명 리스트를 돌며 URL을 일괄 발급하는 서비스 메서드. 콘텐츠 타입 검증은 도메인 서비스 안에 하드코딩된 화이트리스트였습니다.

돌아갔고, 전형적인 V0 질병을 앓았습니다: **수명 관리가 없다.** 업로드됐지만 엔티티에 붙지 못한 파일은 그냥… 남았습니다. 공개·비공개 콘텐츠가 버킷 하나, 접근 모델 하나를 공유했습니다. 새 업로드 유스케이스마다 또 하나의 맞춤 루프가 필요했습니다.

## V1: 버킷 둘과 temp/ 프로토콜

12월의 재작성이 끝까지 살아남은 구조를 들여왔습니다:

- **버킷 2개** — 공개(썸네일·스튜디오 사진, 고정 URL)와 비공개(문서·임시저장, presigned GET 전용).
- **`temp/` prefix 프로토콜.** 업로드는 `temp/`에 착지합니다. 소유 엔티티가 저장될 때 서비스가 각 키를 영구 위치로 *이동*합니다 — S3에 move가 없으므로 copy 후 delete입니다. 7일이 지나도 `temp/`에 남은 것은 정의상 쓰레기고, S3 라이프사이클 규칙이 지웁니다. 애플리케이션 정리와 인프라 정리는 **의도된 이중화**입니다: 버그가 파일을 흘리면 버킷 정책이 백스톱입니다.
- **prefix로서의 소프트 딜리트.** 삭제는 `deletion-scheduled/`로의 이동이고, 또 다른 라이프사이클 규칙이 만료시킵니다. 7일의 되돌리기, 공짜로.

V1의 질병은 인터페이스 증식이었습니다. 공개·비공개 요구가 갈라지며 메서드가 쪼개졌습니다: `generatePresignedPutUrlForPublic`, `...ForPrivate`, 호출처마다 주입되는 검증 콜백. 새 위치 — 임시저장 영역, 신고 증거 스냅샷 보관소 — 가 생길 때마다 메서드 두 개가 늘어날 판이었습니다. (고고학 노트: 이 시기 javadoc 예시에 "트레이너 프로필 사진"이 등장합니다 — 오래된 사이드 프로젝트에서 레퍼런스로 가져온 코드의 유령입니다. 복사한 코드는 유령을 데려옵니다.)

## V2: 정책 테이블

마지막 재작성의 통찰은, 그 모든 메서드가 정확히 두 값에서만 달랐다는 것입니다. 그래서 정책이 데이터가 됐습니다:

```java
public enum FileStorageLocation {
  PUBLIC_PERMANENT (PUBLIC,  ""),
  PUBLIC_TEMP      (PUBLIC,  "temp/"),
  PUBLIC_TRASH     (PUBLIC,  "deletion-scheduled/"),
  PRIVATE_PERMANENT(PRIVATE, ""),
  PRIVATE_TEMP     (PRIVATE, "temp/"),
  PRIVATE_DRAFT    (PRIVATE, "draft/"),
  PRIVATE_REPORT   (PRIVATE, "snapshot/report/"),
  PRIVATE_TRASH    (PRIVATE, "deletion-scheduled/");
}
```

동사 다섯 개짜리 서비스 하나 — `getUploadUrl`, `getViewUrl`, `move`, `softDelete`, `copyToReportSnapshot` — 가 위치를 인자로 받습니다. 그 아래엔 AWS SDK를 import하는 유일한 클래스 `S3Executor`. 그 위엔 규칙 하나: **누구도 경로 문자열을 직접 쓰지 않는다.** 이제 새 저장 영역은 메서드 두 개가 아니라 enum 한 줄입니다.

diff가 제일 좋아하는 부분입니다: **+236 / −268.** 파일 11개, 기능은 늘고, 코드는 순감. 추상화를 하나 *더한* 게 아니라 맞는 추상화를 *찾은* 리팩토링의 서명입니다.

## 치른 값

정직한 흉터 둘. 첫째, V0과 V2 사이 어딘가에서 콘텐츠 타입 화이트리스트가 조용히 사라졌습니다 — 지금 presigned URL은 클라이언트가 선언한 타입을 그대로 서명합니다. 리뷰가 아니라 종료 후 감사에서 발견했고, 정황상 AI 보조 재작성 과정에서 유실됐습니다. 생성된 diff에서 *추가된* 줄만이 아니라 **삭제된 줄을 리뷰하라**는 교훈입니다. 둘째, S3 연산이 DB 트랜잭션 안에서 돌고 보상이 없습니다 — `move` 후 롤백이 나면 스토리지와 DB가 잠시 어긋납니다. `temp/` 라이프사이클이 피해를 한정하는데, 이게 바로 그 중복 백스톱이 밥값을 하는 지점입니다.

**한 줄 요약**: 서비스 인터페이스가 유스케이스마다 메서드를 하나씩 늘리고 있다면, 그 유스케이스들은 아마 당신이 아직 안 쓴 테이블의 행들입니다.
