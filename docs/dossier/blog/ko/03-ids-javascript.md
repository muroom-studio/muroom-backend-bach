# ID가 자바스크립트에 안 들어가던 날

*직접 창업한 5인 스타트업 Muroom 회고 3부작의 마지막. 1부 [사비로 돌린 AWS](/writing/muroom-aws-on-pocket-money), 2부 [JWT를 지운 이야기](/writing/muroom-deleting-jwt).*

---

우리는 일주일 안에 기본키를 두 번 마이그레이션했습니다. 두 번째는 세 시간 걸렸고, 원인은 첫 번째였습니다.

## 1차: 시퀀스 → TSID

스키마는 평범하게 시작했습니다. 테이블마다 하나씩 PostgreSQL 시퀀스 24개, 그리고 `allocationSize = 1`. Hibernate가 INSERT 한 번마다 "다음 번호 뭐예요?"를 물으러 DB를 한 번씩 왕복한다는 뜻입니다.

피드가 최신순으로 정렬되는 서비스라, 애플리케이션에서 생성하는 시간 정렬 ID를 원했습니다. 후보는 셋이었고, 승자가 자명하지 않아서 비교표를 보여드릴 가치가 있습니다:

| | TSID | UUID v4 | UUID v7 |
|---|---|---|---|
| 크기 | **8바이트 (bigint)** | 16바이트 | 16바이트 |
| 시간 정렬 | O | X | O |
| B-tree 삽입 지역성 | append 친화 | 무작위: 페이지 스플릿, 캐시 미스 | append 친화 |
| PG 지원 (2025년, pg 17) | 그냥 `bigint` | 네이티브 `uuid` | 네이티브 생성기 아직 없음 |
| JSON 안전성 | **2⁵³ 넘으면 깨짐** (복선입니다…) | 안전 (애초에 문자열) | 안전 |

UUID v4는 정렬 요건에서 바로 탈락이고, 인덱스 지역성까지 갈아버립니다. 진짜 승부는 시간 정렬이 되는 **v7**과의 싸움인데, 결정타는 폭이었습니다. 우리 스키마는 어디서나 맨 ID 컬럼으로 엔티티를 참조합니다(왜 그런지는 마지막 절에서). 그래서 ID 크기는 한 번 등장하는 게 아니라, **모든 참조 컬럼과 그 위의 모든 인덱스에 곱해집니다.** 8바이트 대 16바이트의 차이가 그대로 구조의 차이가 됩니다. 게다가 2025년 말의 Postgres 17에는 네이티브 `uuidv7()`이 없었고 TSID 라이브러리는 성숙해 있었습니다. TSID의 승리.

롤아웃은 조심스럽게 했습니다. 신규 도메인 하나로 먼저 파일럿, 이틀 뒤 전체 엔티티로 확산하면서 시퀀스 30개를 마이그레이션 하나로 드롭. 이제 ID는 왕복 비용 0에, 공짜로 시간순 정렬됩니다.

눈치채셨을지 모르겠지만, 저 표에는 UUID가 조용히 이기는 칸이 하나 있습니다. 저도 눈치챘습니다. 뒤늦게요.

## 2차: 예상 못 한 쪽

몇 시간 만에 프론트가 "존재하지 않는 엔티티"를 보여주기 시작했습니다. Next.js 개발자 도구가 답을 말해줬습니다. 응답의 ID와 다음 요청의 ID가 달랐습니다. 끝자리 몇 개가.

자바스크립트의 `Number`는 IEEE-754 배정밀도 실수입니다. 정수는 2⁵³ − 1까지만 정확합니다. 64비트 TSID는 그 한계를 가뿐히 넘고, `JSON.parse`는 **조용히** 반올림합니다. 에러도, 경고도 없이. 인접한 엔티티들이 같은 반올림 값 위로 무너집니다.

수정은 지루할 만큼 업계 표준입니다. ID를 문자열로 직렬화하면 됩니다. 하지만 그때의 저는 그걸 몰랐고, 그날 오후에 올린 PR에는 제가 코드 리뷰에 쓴 문장 중 가장 아끼는 문장이 아직 남아 있습니다:

> "진짜 이렇게 해야 되나? 실무에서도 이렇게 해?"

합니다. 트위터 API는 정확히 이 이유로 2010년부터 모든 숫자 ID 옆에 `id_str` 필드를 함께 실어 보냅니다. 그날 33개 파일을 고친 뒤, 코드베이스의 모든 응답 DTO는 문자열 ID를 반환하게 됐고, 이 규칙은 이후 만든 모든 것에 그대로 이어졌습니다.

## 더 조용했던 마이그레이션: 외래키를 지우다

한 달 뒤, 같은 직감(*이건 데이터베이스가 있을 자리가 아니다*)이 한 발 더 나갔습니다. 자문을 구한 현업 백엔드 엔지니어의 조언에 따라, 스튜디오 도메인의 FK 제약을 전부 드롭했습니다. 14개였습니다.

그의 논거는 학술이 아니라 운영이었습니다. 실사용자 이슈로 소방수 노릇을 할 때, FK 체인은 데이터를 만질 수 있는 *순서*를 강제합니다. 그리고 우리 스키마 전체가 기대고 있던 소프트 딜리트 패턴(부모 행은 `deleted_at` 뒤로 사라지고 자식 행은 계속 사는)을 정면으로 거스릅니다. 그래서 우리의 규칙이 됐습니다: **데이터베이스는 완화하고, 코드에서 강제한다.**

크로스 도메인 참조는 맨 `studio_id` bigint 컬럼으로 줄었습니다. 정합성 검사는 서비스 레이어로 옮겨졌습니다. 소프트 딜리트 아래의 유니크 문제는 부분 유니크 인덱스(`WHERE deleted_at IS NULL`)로 제대로 풀었습니다. 탈퇴한 사용자의 닉네임은 재사용할 수 있되, 살아 있는 계정 하나만 가질 수 있게.

## 다시 하라면?

은행에서라면? 아니요. 그리고 그게 핵심입니다. 이 결정들은 우리 맥락에서만 말이 되는 것들이었습니다. 애플리케이션 생성 64비트 ID는 삽입 처리량과 공짜 정렬을 사줬고, 그 값으로 우리는 프론트엔드와의 계약을 아프게 배웠습니다. FK 없는 스키마는 운영의 자유를 사줬고, 그 값으로 애플리케이션이 정합성 노동을 떠안았습니다.

TSID 선택조차 재채점이 필요합니다. Postgres 18에는 이제 네이티브 `uuidv7()`이 실렸으니, 우리가 결정하던 때보다 생태계 논거는 좁아졌습니다. 폭 논거는 그대로지만, 이렇게 맥락적인 결정은 방어할 게 아니라 다시 돌려봐야 합니다.

어떤 맥락에서든 가져갈 메타 교훈은 이겁니다. **ID 타입과 제약 조건은 하류의 모든 시스템과 맺는 API 계약입니다. 십진수라는 걸 깜빡한 그 자바스크립트 런타임까지 포함해서.**
